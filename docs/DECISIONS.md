# DECISIONS.md — Architectural decisions and tradeoffs

The code does not contain a formal ADR directory. Items marked **Inferred** derive from implementation and project history rather than an explicit design-record sentence.

| Decision | What the implementation does | Why / tradeoff / alternative |
|---|---|---|
| Single-owner Google allowlist | `PORTABLE_AUTH_ENABLED=true` requires a Google ID token whose verified email equals `OWNER_GOOGLE_EMAIL`; it creates one durable admin row. | **Inferred:** private personal use avoids multi-user enrollment, password reset, and role administration. Tradeoff: access depends on Google OAuth configuration and the owner account. Alternative: passkeys/WebAuthn or conventional account/password system. |
| Server-only provider keys | Browser selects only `"gemini"`/`"groq"`; `generatePortableDraftText()` obtains secrets from server env. | Prevents browser key theft. Tradeoff: all drafting requires a server function. Alternative: client-side direct provider calls, rejected for security. |
| Explicit provider selection, no auto-failover | Local storage remembers the selected provider; Gemini is default; Groq only runs when chosen. | **Inferred:** preserves user control, avoids unexpected cost/model/provider changes, and makes rate-limit failures diagnosable. Tradeoff: user must manually switch after a quota error. Alternative: automatic fallback with clear audit/cost policy. |
| Grounded generation plus post-generation gates | `aiPrompts.ts` restricts source facts, while `draftQuality.ts` and `onePageResume.ts` reject incomplete/overlong drafts and retry targeted repairs. | **Inferred:** prompt-only safety is insufficient for factual career material. Tradeoff: more model calls and possible completion failure. Alternative: accept one model response without validation. |
| Role-based No JD mode is distinct | `contextMode="limited"` uses role title as a broad ordering signal but explicitly does not claim employer requirements. | Avoids falsely pretending a title contains a job description. Tradeoff: less specific tailoring. Alternative: infer a standard JD, rejected because it invites fabrication. |
| Preview/approval before use | Exports and Gmail attachment require `tailoredResumeApprovedAt` and one-page fit. Content edits reset approval. | **Inferred:** human review protects accuracy and prevents accidental use of unreviewed generated content. Tradeoff: an extra user action. Alternative: immediate download/attachment. |
| Draft-only Gmail integration | Code calls Gmail `drafts` endpoint and never `messages.send`; UI says manual send. | Preserves human agency and reduces mis-send risk. Tradeoff: no one-click application automation. Alternative: send mail automatically, intentionally excluded. |
| No raw resume storage in portable mode | `portableResumeTextRequired()` is true; PDF upload is rejected. | **Inferred:** eliminates an R2/S3 account/card requirement and reduces sensitive file retention. Tradeoff: owner must paste text and store originals elsewhere. Alternative: S3/R2/GDrive file store. |
| Generated document bytes are ephemeral | Exports happen in browser; Gmail DOCX is created from approved text in memory. | Limits persistence and storage costs. Tradeoff: source DOCX is regenerated rather than retrieved. Alternative: persistent document/object storage. |
| Vercel + TiDB serverless deployment | `vercel.json` builds migrations plus assets and routes all traffic to one function. | **Inferred:** affordable portable hosting with a managed MySQL-compatible database. Tradeoff: cold starts and migration-on-build risk. Alternative: persistent VM + local MySQL or a container service. |
| tRPC rather than handwritten product REST | `server/routers.ts` defines typed procedures consumed through `client/lib/trpc.ts`. Only OAuth/Gmail uses REST because redirects/webhooks do not fit RPC. | **Inferred:** types flow from server to React and reduce client contract duplication. Tradeoff: third-party API consumers cannot easily use the application API. Alternative: OpenAPI REST/GraphQL. |
| One Express factory for local/Vercel | `createApiApp()` excludes static serving; runtime entries add static/Vite behavior. | Avoids divergence between development and serverless behavior. Tradeoff: asynchronous bootstrap and build packaging complexity. Alternative: separate apps. |
| Defensive cookie parsing/state checks | `parseRequestCookies()`, `equalState()`, same-origin route check, and no throw on malformed unrelated cookie. | **Inferred:** production cookies can be malformed/foreign; auth should fail closed, not crash. Tradeoff: slightly more local security code. Alternative: optimistic simple parsing. |
| Application data stays relational, profile links stay JSON | Jobs/profiles/connections use SQL tables; `contactLinks` is a serialized object. | **Inferred:** core fields need SQL query/index behavior, while fixed optional links do not justify five sparse columns. Tradeoff: SQL cannot directly query link fields. Alternative: normalized contacts table. |
| Job discovery uses targeted redirects | `jobDiscovery.ts` constructs board search URLs instead of reproducing job listings. | **Inferred:** avoids scraping/terms burden and expensive API dependencies. Tradeoff: owner leaves the app to inspect full listings. Alternative: API-backed listing ingestion/cache. |
| Full document layout is rule-based | Client/server resume parsers strip Markdown fences/dividers and turn known header links into proper DOCX/PDF hyperlinks. | **Inferred:** stable ATS-friendly documents are more dependable than rendering arbitrary Markdown/HTML. Tradeoff: supported formatting is intentionally constrained. Alternative: rich-text/HTML or template editor. |

## Consequences to preserve

The product is intentionally **not** an unattended job-application bot. A user must review generated material, approve the resume, and manually send email. The only durable sensitive content is the owner profile/job data in TiDB and an encrypted Gmail refresh token; no original resume file, provider key, or Gmail access token is stored in browser state.

When extending the project, treat any feature that changes one of these boundaries—multi-user access, auto-send, raw-file retention, background scraping, or client-side AI calls—as a new product/security decision rather than a small implementation detail.
